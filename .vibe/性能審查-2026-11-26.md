# 性能審查 2026-11-26（分支 work/return）

三個子代理分三區看完（資料層與計算、畫面與立繪動畫、啟動／小工具／背景），主會話逐條抽查程式碼，下面列的都對過原始碼。全程唯讀，沒有改檔。沒有在真機或 Instruments 上量過，毫秒數都是推估。

## 結論

沒有 O(n²) 等級的演算法問題，小工具、Siri、內購、通知、立繪動畫的寫法都對。

問題集中在一件事：同一份 Digest（境界、功法、走勢全部的摘要）被重算太多次，而且每次都要把全部紀錄從 SwiftData 讀出來從頭算。幾百筆時感覺不到。長期使用者累積到兩三千筆修煉以後，回前景、記一筆、改設定都會頓一下。

另外有三個地方在「打字」或「按住加減」時每一格都做重工作，資料少也可能感覺得到。

## 立繪動畫：沒問題

- 只有境界碑用到 `*Anim` 大圖（`Views/Realm/SteleView.swift:166`），一次只解碼 1 張，約 13.5MB。
- 切格是把整張圖用 `.offset` 移位再 `.clipped()`，每 0.15 秒只改位移，不會重新裁切或解碼。
- 選造型頁十二格用的是靜態小圖，合計約 1.8MB。
- 磁碟上那 49MB 只影響下載大小，執行時的記憶體跟它無關。

## 一、Digest 算太多次（根因，一次改可以解掉一串）

| 位置 | 現在的寫法 |
|---|---|
| `App/RootTabView.swift:52`、`:182` | Digest 寫在 body 裡，沒有快取。回前景一次 scenePhase 變好幾次、`healthStatus` 變兩次、`purchases.refresh()` 重設 `ownedProductIDs`，每次都整份重算，估計一次回前景算 4 到 7 次 |
| `Services/StoreService.swift:183` | `save()` 不管有沒有改到東西都跑 `afterSave`，裡面再撈全表算一份 Digest 給小工具，然後無條件 `reloadTimelines`。換造型、改道號、開關提醒也一樣 |
| `Services/StoreServiceBulk.swift:96` | 開著健康讀取的人每次回前景，健康 app 沒新資料也會 `save()`，連帶整套重算 |
| `App/RencanApp.swift:48` | 打開 app 時在 `init` 裡同步算一份，第一個畫面要等它算完才出來。畫面出來後 body 又算一次 |
| `Intents/LogLiftIntent.swift:31` | app 沒開時用 Siri 記一筆，init、intent、存檔後各算一次，共三次 |

建議改法：

1. `save()` 開頭加 `guard context.hasChanges else { return }`，沒改到東西就不存、不觸發快照。
2. StoreService 加一個每次存檔加一的 `revision`，Digest 用 `(revision, today, 身高, 性別)` 當鍵快取起來。body 和小工具快照都從快取拿，資料沒變就不重算。
3. 打開 app 那次快照移到 `RootTabView` 的 `.task`，等第一個畫面出來再寫。
4. 小工具快照寫入前跟舊的比，內容一樣就不寫、不 `reloadTimelines`。

前提是所有寫入都走 `save()`，藍圖 a10 本來就這樣規定。

## 二、打字或按住時每一格都做重工作

| 位置 | 情境 | 改法 |
|---|---|---|
| `Views/Share/ShareCardSheet.swift:76` | 修煉卡頁打道號，每按一個注音鍵就在主執行緒用 `ImageRenderer` 以三倍畫一張 1080×1920 的卡（約 8MB 點陣圖）。舊手機打字會黏 | `.task(id:)` 裡先 `Task.sleep` 300 毫秒，沒被取消才畫 |
| `Views/Settings/SettingsView.swift:97` | 設定頁按住身高加減，`HeightStepper` 每走一格就 `saveProfile`，觸發存檔、小工具快照、整份 Digest 重算 | 畫面先顯示暫存數字，停手 0.4 秒才存 |
| `Views/Log/LiftFormView.swift:190` | 記一筆表單每次重畫都掃全部修煉找「上次」，`bodyweight(on:)` 又重排一次量測。按住加減重量時每格都跑 | 打開表單時算一次存進 `@State`，換日期才重算體重 |

## 四、特定情境才會碰到

- `Services/StoreServiceBulk.swift:87`：從健康 app 重建歷史時，每一筆都用 `measurement(on:)` 查一次資料庫。換手機第一次打開、或在設定按重建時會碰到，健康 app 有上千天資料時可能卡一兩秒。改成先撈一次已有的日期放進 `Set`。
- 同一個函式還有一個不是性能的問題：`Validation.check` 在迴圈中間丟錯時，前面已經 `insert` 的幾筆沒有退回，會在下一次任何 `save()` 時一起存進去。建議先全部驗證完再插入，跟 `checkImport` 一樣。
- `App/RootTabView.swift:126`、`Services/HealthKitService.swift:117`：app 裡還沒有任何量測、健康 app 又只有體重沒有體脂時，每次回前景都把全部健康歷史讀一遍。記下上次掃到哪一天就好。

## 五、理論上，現在不用動

- `Views/Realm/SteleView.swift:99`：立繪動畫只看前景、減少動態、低耗電，切到別頁或開表單時還在跑。可以加上「在境界頁、沒開表單、沒在慶祝」三個條件。
- `Views/CelebrationParticles.swift:136`：粒子 1.9 秒散完，畫面更新跑滿 4.5 秒。
- `Services/PurchaseService.swift:108`：每次回前景都向 App Store 重抓 12 個商品價格，可以改成打開選造型頁時才抓。
- `Services/DayStamp.swift:7`：`calendar` 是每次重算的屬性，改成 `static let`。
- `Views/Realm/SteleView.swift:80`：陰影包住整塊含立繪的內容，立繪每格換圖陰影就重算。改成陰影只掛在底色形狀上。境界碑不要加 `.drawingGroup()`，那會把 4032×3360 的整張圖先畫進暫存畫布。

## 建議順序

1. 先在 RencanCore 加一條量時間的測試：塞 3000 筆修煉、200 筆量測，量一份 Digest 要幾毫秒。檢查線上就能跑，有了實際數字再決定第一區要做到多細。
2. 第一區（Digest 快取、沒改不存、啟動延後、快照沒變不重畫）。改完二、三區的影響會跟著變小。
3. 第二區三個打字與按住的問題。
4. 第三區 `RecentLiftsList` 與 `MoveDetailView`，加上第四區健康重建的逐筆查詢。

每一步都在新分支做、檢查線全綠再往下。
