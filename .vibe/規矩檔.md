# 規矩檔（AI 每次動工前必讀）

## 通用 AI 行為基準（從專案第一天起就成立，勿改）

1. **不准猜假設，不確定就問。** 收到任何指令，若有不明確的詞、有多種可能的解讀、缺少關鍵資訊——**停下來把不明確的地方列出來問使用者**，不要替他選一個解讀就動手。靜默的假設是這套系統最大的失敗源頭。

2. **每一行改動都必須能追溯到使用者的明確要求。** 不准順手「改進」相鄰的程式碼、不准重整不相干的格式、不准刪掉「看起來像死碼」但不在這次任務範圍內的東西、不准做沒被要求的重構。每一行 diff 都要對得上一句使用者講過的話。
   - **（刻意反「童子軍原則」，重要）**：工程界有條「童子軍原則／破窗效應」——路過爛 code 順手修乾淨。**這套系統故意不這樣做**：對看不懂程式碼的人，「順手清理」是**驗不到的暗改**，一個 drive-by「整理」可能靜默弄壞別處而他永遠看不到。所以**破窗要修，但要用一片正式的 `vibe-simplify`（走過審核）去修，不准路過時即興順手改**。清理是一個被切出來、驗得到的動作，不是夾帶在別的任務裡的副作用。

3. **不准加沒被要求的功能、抽象、設定項。** 「想說以後可能會用到」「順便寫得更彈性一點」「加個 config 比較好」——全部不准。要做的事跟使用者要的事一對一，多的一律砍。（注意：這條禁的是替想像情況**鍍金**；下面第 4 條的健壯性地板是**最低要求**，不在此限。）

4. **錯誤要大聲、輸入要驗、爆了要倒向安全側（健壯性地板）。** AI 寫的程式表面會跑，但**邊界與錯誤處理常常是空的**——而看不懂程式碼的人看不到空的 catch、看不到沒驗證的輸入。這四條是地板，寫任何程式一律遵守（這不是第 3 條禁的「鍍金」：錯誤一定會發生，差別只在「大聲報」還是「默默吞」）：
   - **快速失敗、不准默默吞**：一發現不對就大聲報錯停下，**不准用空的 catch 把錯誤吃掉繼續跑**。吞掉的錯不會消失，只會用更難懂的形式在更遠的地方爆。
   - **外部進來的一律先驗證**：使用者輸入、API 回傳、檔案內容——用之前先檢查，絕不假設它是好的（這同時是健壯性與安全的根）。
   - **爆掉時倒向「拒絕／鎖住」，不是「放行」**：尤其權限／付費／安全相關，出錯的預設是「不准」，不是「那就讓他過吧」。
   - **保護式子句**：不合法的狀況在函式開頭就擋掉提早 return，讓正常路徑保持平坦，不要把主邏輯埋在層層巢狀 if 裡。

## 專案特定規矩（AI 憲法，vibe-voice-lock 於 2026-11-07 立）

> 這段約束 AI 的「判斷」。格式與可驗證的規則由 hook 強制執行（本機 `.vibe/hooks/pre-commit.js` 做文字層檢查；GitHub Actions 跑 swift-format 與 SwiftLint），不在此重複。
> 每一條都是「做／不做」的動作，不是形容詞。

### 0. 前提
- 格式不用管，swift-format 會處理；不要為了排版花任何推理。
- 動手前先讀鄰近檔案，模仿既有結構；第一片之後，每個新檔都要長得像同資料夾已有的檔。
- 檔案與資料夾只准照 `.vibe/架構藍圖.md` 第三節的計畫放；要加一個計畫外的檔或資料夾，先回去改藍圖。

### 1. 架構邊界
- 三個 target 一個套件：主 app（ios/Rencan）、小工具（ios/RencanWidget）、規則引擎套件（ios/RencanCore）。算法只准住在 RencanCore；畫面不准自己算境界、功法、宗門、突破。
- RencanCore 只 `import Foundation`，不碰 SwiftUI、SwiftData、HealthKit，要能在 Linux 跑測試。日期在 RencanCore 裡用跟網頁版一樣的「yyyy-MM-dd」字串，天數差用同樣的算法，為了算得一模一樣。
- 畫面結構最薄：一個畫面一個 View 檔；資料用 SwiftData 的 `@Query` 直接在 View 讀；服務（StoreService、HealthKitService 等）是 `@Observable` 物件從 environment 注入；不另造 ViewModel 層，除非同一份狀態要被兩個以上畫面共用。
- 不准引入 Coordinator、VIPER、Repository、Clean Architecture、Redux 式 store 或任何藍圖沒寫的架構模式。
- 不准為單一型別先抽 protocol；要有第二個實作才抽。不准 protocol 加 associatedtype 的泛型體操。
- 不准沒理由把同步邏輯包成 async 或 Combine；HealthKit、檔案匯入這種本來就 async 的才 async。
- 零第三方套件。要加先回來改藍圖與安全標準。

### 2. 反過度工程禁令
- 不准為「未來可能會用到」加參數、抽象層、config 開關、protocol、泛型。要用到那天再加。
- 新功能預設寫成一個函式；要拆檔、拆型別、引入抽象前，先停下來問。
- 不准加定稿「明確不做」裡的任何東西，包含 iCloud、帳號、課表、每組逐筆、女性表、教學頁。
- 不准多一個必填欄位或多一頁引導（定稿「邊界」）。
- 不准在表單、Siri、匯入三個入口各寫一套驗證；驗證規則只住在 RencanCore 一處，三個入口都呼叫它。

### 3. 可讀性鐵則
- 命名要表達意圖：`elapsedDays` 不是 `d`、`bestLiftByMove` 不是 `best`、`bodyFatPercent` 不是 `bf`。網頁版的縮寫變數名搬過來時一律改成完整名，對照表寫在 RencanCore 的檔頭註解。
- 註解寫「為什麼」不寫「做什麼」：只記取捨、踩過的雷、跟網頁版對齊的理由。註解用繁體中文。
- 不留魔術數字：20（體脂門檻）、0.5（每期 FFMI）、4.5（慶祝秒數）、5（復原秒數）這類數字都要有名字，住在 Tables 或一個常數檔，改只改一處。
- 最小驚訝：函式不准偷偷做名字沒說的事；`save` 不順便刷新小工具以外的東西，`delete` 不順便改設定。

### 4. 錯誤、輸入、日誌（接規矩檔第 4 條與安全標準）
- 不准 `try?`、不准空的 `catch {}`；錯誤一律往上丟到畫面，用 `RencanError` 列舉帶中文訊息顯示。
- 不准 `print`、`NSLog`、`debugPrint`、`os_log` 在 app 與小工具的程式碼裡出現；測試裡可以。
- 錯誤訊息不夾帶數值（寫「體重超出範圍」，不寫數字）。
- 不准寫死色碼：顏色只從 Assets 的顏色集經 `Color.rencan.*` 取；字體只從一處取；畫面檔裡不准出現 `#`、`Color(red:`、`UIColor(red:`。
- 不准 `NSAllowsArbitraryLoads`、不准 CloudKit、不准任何 HTTP 呼叫。
- repo 永遠沒有 .p12、.p8、.cer、.mobileprovision、.pem、.key；工作流不准 echo secrets。

### 5. AI 行為準則
- 改既有的，不要新增：優先修改現有的型別、函式，而不是另開一個名字相近的。
- 建新檔前先掃同資料夾，不要重複造工具函式。
- 每一片只動帳本「本片動到的檔」那幾個檔；順手改到別的檔就停下來。
- 不確定就選最無聊、最少程式碼、最像鄰近檔案的那個做法，然後問。

### 6. Swift 版本與平台
- Swift 5.10 語法、iOS 17 API；不用 iOS 18 以上才有的 API，要用先回來改藍圖技術基線。
- 不用 `@MainActor` 以外的手寫執行緒控制；SwiftData 與 HealthKit 的 async 呼叫在 Task 裡 await。

## 安全標準

- 專案類型：Mobile App（iOS 原生）＋通用 CWE 兜底（匯入檔案、CI 腳本）
- 適用標準：OWASP MASVS、CWE Top 25、App Store 審核規範 5.1.3（健康）
- 完整清單見 `.vibe/安全標準.md`
- 上線前必跑：vibe-security-gate（階段 C）
- 三條寫程式時就要守的：健康數值不進 log、不進 URL；量測不進 iCloud；repo 永遠沒有憑證與金鑰
