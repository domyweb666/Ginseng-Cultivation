# 安全標準（這個專案的自查表）

> 這份檔案由 `vibe-security-gate` 在初始化階段（階段 A）建立，2026-11-07。
> 它的功能是：
> 1. 給 AI 看：後續寫任何畫面、服務、意圖、工作流時，要先過這份清單
> 2. 給你看：準備上線時，對著這份逐項自查
>
> **這不是合格證書，是自查表。** 真正的安全審計需要專業團隊。

---

## 這個專案的類型

**已確認類型（2026-11-07 你點頭）**：Mobile App（iOS 原生）＋通用 CWE 兜底（匯入檔案、CI 腳本）

**判定時間**：2026-11-07

**判定依據**（依 `.vibe/架構藍圖.md`，不依舊檔案結構）：

- ☑ Mobile App（信心 95%）：藍圖是 SwiftUI app、ios/ 專案、HealthKit、WidgetKit、App Intents。
- ☐ Web 應用（信心 30%，應該不套）：repo 裡的 index.html 是舊的 PWA，這次只加一顆匯出鈕；靜態單頁、沒有後端、沒有登入，不套 web 標準。
- ☐ 純 API 服務（0%）：沒有後端。
- ☐ 有調用 LLM（0%）：沒有。
- ☐ CLI／桌面（20%）：GitHub Actions 工作流與 openssl 憑證腳本屬這類，用通用 CWE 兜底，不另列類型。

## 給 AI 的指令（system instruction）

> 後續寫任何畫面、服務、App Intent、小工具、工作流時，**每寫完一片**必須自查以下清單。
> 找到問題立即修，不要等到上線前才補。
> 三條寫程式時就要守的：健康數值不進 log、不進 URL；量測不進 iCloud；repo 永遠沒有憑證與金鑰。
> 2026-11-18 加第四條：內購出錯一律當沒買，買過什麼只問 Apple，app 不自己存（類別 10）。

## 必查清單

### 類別 1：本機儲存（MASVS-STORAGE）

被打中會怎樣：攻擊者拿到手機或備份檔，看到使用者的體重體脂歷史。

- [ ] 量測與修煉存在 app 沙盒的 SwiftData 資料庫，靠系統 Data Protection（預設就有）；不關掉、不改成 NSFileProtectionNone
- [ ] 絕不把體重、體脂率、去脂體重寫進 print、NSLog、os_log；錯誤訊息不夾帶數值（寫「體重超出範圍」，不寫「體重 83.2 超出範圍」）
- [ ] App Group 的小工具快照只放顯示需要的（境界名、期別、本週天數、累計天數、距下一期差幾 kg），不放原始量測清單
- [ ] 匯出的 JSON 是健康資料：匯出時顯示一句「這個檔案含你的身體數據，自己保管」
- [ ] 不把任何資料放進 URL 或深連結參數；深連結只帶分頁名
- [ ] 截圖防護、退到背景遮蔽：N/A（境界畫面本來就是給人截圖的；2026-11-18 起有內購，但付款視窗是 Apple 的，app 自己沒有付款頁）
- [ ] 存 token、密碼：N/A（沒有帳號）

### 類別 2：加密（MASVS-CRYPTO）

- [ ] 不自己寫加密、不用 MD5、SHA-1；紀錄 id 用系統 UUID；其餘 N/A（資料加密靠系統 Data Protection）

### 類別 3：網路（MASVS-NETWORK）

被打中會怎樣：中間人攔到資料。這個 app 自己不連網，風險主要是「之後有人順手加一個 HTTP 呼叫」。

- [ ] app 自己不發任何 HTTP 請求；唯一對外是 HealthKit、通知、StoreKit 內購（2026-11-18 加，連的是 Apple 的伺服器）、App Store Connect 上傳（CI 端），全部走 Apple 框架
- [ ] 不關 ATS：Info.plist 不出現 NSAllowsArbitraryLoads
- [ ] 隱私政策連結用 https
- [ ] Certificate pinning：N/A（沒有自家伺服器）

### 類別 4：驗證與授權（MASVS-AUTH）

- [ ] N/A：沒有登入、沒有 token。之後若要加帳號，先回來改這份

### 類別 5：平台互動（MASVS-PLATFORM）

被打中會怎樣：別的 app 或惡意連結用深連結、捷徑參數塞怪東西進來。

- [ ] 深連結（通知、小工具、Siri 開 app）只接受固定的分頁名清單，其他一律忽略
- [ ] App Intents 的參數（功法、重量、次數、組數）走跟表單一樣的驗證，不信任 Siri 給的值
- [ ] 沒有 WebView；不註冊 URL scheme；外部檔案只接受匯入，匯入走完整驗證

### 類別 6：程式碼品質（MASVS-CODE）

- [ ] 用最新穩定的 Xcode 與 iOS SDK 建置；最低 iOS 17
- [ ] 零第三方套件（藍圖已定）；之後若要加，先回來改這份並鎖版本
- [ ] 例外：自家套件 VeggieKit（2026-11-19 加，github.com/domyweb666/VeggieKit），專案檔鎖死在 1.0.0（exactVersion），升級要改專案檔、重跑 CI。它只有設定頁的畫面元件：不發 HTTP、不讀寫健康資料；意見回饋的信只帶 app 版本、iOS 版本、機型、語言，不帶任何體重體脂
- [ ] Swift 記憶體安全；不用 unsafe 指標、不橋接 C

### 類別 7：抗逆向（MASVS-RESILIENCE）

- [ ] 不做越獄偵測、不混淆。2026-11-18 起有內購，碰到錢了，但只賣造型圖，被破解的損失是一種造型的錢，為它加越獄偵測划不來；防白送靠類別 10 的「只認 Apple 驗證過的交易」

### 類別 8：隱私（MASVS-PRIVACY 加 App Store 5.1.3）

被打中會怎樣：上架被退、或使用者覺得 app 偷他的健康資料而給一星。

- [ ] HealthKit 只申請四種讀取（體重、體脂率、去脂體重、身高）與三種寫入（體重、體脂率、去脂體重）；不多要
- [ ] 兩段授權說明文字講人話：讀是為了算境界，寫是你自己打開的選項
- [ ] 讀取授權在第一次打開問一次；寫入在使用者打開回寫時才問；拒絕後 app 照常可用
- [ ] PrivacyInfo.xcprivacy：列出用到的「必須說明原因的 API」（UserDefaults 等）與蒐集的資料類型（健康與健身）
- [ ] App Store 隱私標籤：健康與健身資料，「不與使用者身分連結」「不用於追蹤」
- [ ] 健康資料不用於廣告、不給第三方、不做分析（5.1.3 i）；app 裡沒有任何分析或廣告 SDK
- [ ] 不寫假的或推算的數字進 HealthKit（5.1.3 ii）：只回寫使用者手打的三種；去脂體重若是算出來的不寫
- [ ] **不把個人健康資料存進 iCloud（5.1.3 ii）**：量測（體重、體脂率、去脂體重）不進 CloudKit；跨裝置靠健康 app 本身。這條推翻了定稿「iCloud 同步第一版就開」的預設，見 `.vibe/架構藍圖.md` 第八節第 4 點
- [ ] 提供「刪除全部紀錄」：設定裡一鍵刪本機全部資料（含小工具快照）；回寫進健康 app 的由使用者在健康 app 刪，說明寫清楚。定稿沒列、安全標準要求，待你確認
- [ ] 第三方 SDK 的資料蒐集：N/A

### 類別 9：通用 CWE（匯入與 CI）

被打中會怎樣：壞的匯入檔污染資料、憑證外洩讓別人能用你的名義發 app。

- [ ] CWE-20 輸入驗證：表單、Siri、匯入 JSON 三個入口都驗型別與範圍；匯入全驗完才寫，絕不寫一半
- [ ] CWE-502 不安全反序列化：匯入只用 Codable 解 JSON；不用 NSKeyedUnarchiver 解外來檔
- [ ] CWE-22 路徑穿越：匯入只用系統檔案選擇器給的安全範圍 URL；不自己拼路徑
- [ ] CWE-798 硬編碼秘密：repo 永遠沒有 .p12、.p8、密碼；只放 GitHub Secrets；.gitignore 擋 *.p12、*.p8、*.mobileprovision、*.cer
- [ ] CWE-78 指令注入：CI 工作流的 shell 步驟不把任何外部字串（PR 標題、分支名、commit 訊息）拼進指令；secrets 不 echo、不寫進紀錄
- [ ] CI 鑰匙圈：暫時鑰匙圈、隨機密碼、工作結束刪除；工作流只在 main 與自己的分支跑；來自 fork 的 PR 拿不到 secrets（GitHub 預設，不要改）
- [ ] 內購商品工作流 `iap.yml`（2026-11-18 加）：只能手動觸發、只准在 main 跑；用跟上傳 TestFlight 同一把 App Manager 等級的 API 金鑰，金鑰還原到暫存路徑、跑完一定刪、不印內容；預設 check 只讀，create 才改；商品資料全驗過才打 API，產品 ID 格式不對或重複就一個都不建
- [ ] Limrun（第三方雲端模擬器，2026-11-07 納入）：上傳到 Limrun 的只有 app 建置檔，不含任何使用者資料；`LIM_API_KEY` 只放 GitHub Secrets 與本機環境變數，不進 repo；模擬器測試只用合成資料，不放真實體組成；`@limrun/api` 鎖死版本（`ios/ci/package.json`、`.vibe/tools/package.json`），不用未鎖版本的全域安裝；模擬器用完就刪（腳本 finally 一定刪，另設 hardTimeout 12 分鐘兜底）
- [ ] 內購的 StoreKit 測試設定檔（`.storekit`，2026-11-18 加）只掛在 Debug 與 UI 測試的 scheme；TestFlight 與上架的建置走真的 App Store（TestFlight 是沙盒）。測試設定檔裡的產品 ID 跟 `ios/ci/iap_products.json` 一字不差

### 類別 10：內購（2026-11-18 加，組塊 M；依據 `.vibe/付費造型計畫.md`、App Store 審核規範 3.1.1）

被打中會怎樣：兩種壞法。一是白送：出錯、被改設定、被竄改時造型變成可用，付費失去意義。二是吃錢：使用者付了錢卻一直鎖著，他會去申請退款、留一星。

- [ ] 出錯倒向鎖住：讀不到商品、交易驗證失敗、網路斷線、不認得的產品 ID，一律當沒買。選造型頁顯示鎖，境界碑與慶祝顯示原版；記錄、算境界等功能不受影響
- [ ] 只認 Apple 驗證過的交易：買過什麼只看 `Transaction.currentEntitlements` 與購買回來的 `VerificationResult`，`.unverified` 一律當沒買；不信任任何別的來源（啟動參數、深連結、匯入檔、Siri 參數都不能讓造型變成可用）
- [ ] 不在本機存「已購買」旗標：UserDefaults、SwiftData、App Group、鑰匙圈都不存「買了哪幾種」。每次要判斷都問 StoreKit。設定裡存「目前選的造型」可以，但畫面顯示前要先對過 Apple 的購買狀態，沒買就畫原版
- [ ] 退款與撤銷：交易的 `revocationDate` 有值就當沒買；app 有監聽 `Transaction.updates`，退款或撤銷傳進來時跟著變回鎖住
- [ ] 沒有伺服器、沒有帳號：不架收據驗證伺服器、不接 App Store Server Notifications、不用 RevenueCat 這類第三方套件；購買紀錄由 Apple 管
- [ ] 價格字串用 Apple 給的 `Product.displayPrice`：app 程式裡不寫死「NT$120」「NT$480」，換地區、換幣別、Apple 調價都跟著對
- [ ] 審核規範 3.1.1：非消耗性項目要有「恢復購買」，放在選造型頁、看得到、不用先點別的地方；按了呼叫 `AppStore.sync()`，成功失敗都要有一句白話回應
- [ ] 審核規範 3.1.1：數位內容只走 Apple 內購；app 裡沒有任何外部付款連結、沒有寫「去網站買比較便宜」
- [ ] 每一筆完成的交易都呼叫 `finish()`；沒 finish 的交易下次啟動會一直再送進來
- [ ] 購買相關的 log 不印交易內容、不印 Apple 帳號資訊；錯誤訊息講白話，不把 StoreKit 的英文錯誤直接丟給使用者
- [ ] 按鈕字寫「購買」，不寫「解鎖」（多米的寫作禁用詞）；價格與「恢復購買」在付款前就看得到，不藏條件
- [ ] 隱私：加了內購之後 App Store 隱私標籤要不要改，判斷寫在 `docs/上架隱私填寫清單.md`「內購之後」那一段；之後若加伺服器驗證或購買分析，那一段要重判

## 上線前流程

當你說「準備上線了」、「跑安全檢查」時：

1. 觸發 `vibe-security-gate` 階段 C
2. AI 對著這份 `.vibe/安全標準.md` 逐項檢查現有程式碼
3. 產出 `.vibe/安全檢查報告.md`
4. 全綠 → 可上線；有紅 → 必修

## 邊界提醒（這份不能做到的事）
